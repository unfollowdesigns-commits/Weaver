How Weaver works, step by step

Three paths. One runs by itself, one runs when someone types in Claude, one runs when the team wants a client report. The colored chip on each step says where it happens.

Phase 2 · prepared
Path A · runs by itself

From "candidate added" to a score on the card

About a minute per candidate. Nobody has to press anything.

  1. A recruiter adds a candidate to a searchLoxo, as usual

    Nothing changes in how the team works.

  2. Loxo tells WeaverLoxo → Render

    Loxo sends a short message to Weaver's address on Render: "person 123 added to search 45". This is the webhook we register once at setup.

  3. Weaver checks before spending anythingRender

    Is this search switched on? Has this person already been scored here? Is today's spending cap reached? If any answer stops it, nothing is paid for.

  4. Weaver reads the candidate from LoxoLoxo, read only

    Profile, work history, the resume text and the team's notes.

  5. Weaver prepares the recordRender

    Removes name, email, phone, address, pay and graduation years. Picks the search's own scorecard (the nine criteria Josh approved), or the standard one.

  6. Claude reads and scoresClaude

    One request per candidate, on the firm's Anthropic account. Claude must answer in a fixed format: nine scores with evidence, Yes or No, star, strongest signal, watch item, where they fit, where to probe.

  7. Weaver checks the answerRender

    Rejects anything incomplete and asks once more. Computes the average itself, so it always matches the scores. Adds flags (no resume, thin record).

  8. The score lands on the candidate in LoxoRender → Loxo, write

    As a scorecard marked "AI, awaiting review": 4.1 / 5 · Yes, the reasons, where to probe. Nothing else in Loxo is touched. Off until Josh approves the dry run.

  9. The team decidesPeople

    They read it, agree or not, call or not. Weaver never moves or rejects anyone.

Safety net, every hour

A second small job on Render looks for anyone on the switched-on searches without a score (a missed message, the cap reached yesterday) and scores them through Claude's half-price batch service. It also reads from Loxo and writes back exactly like steps 4 to 8.

Path B · runs when someone types

Josh asks Claude a question

No Render here. This is Loxo's own connector inside the firm's Claude. We switch it on once at setup.

  1. Josh types in Claudeclaude.ai

    "Top 3 on the VP Sales search, and why?" or "Prep my call with Candidate B."

  2. Claude asks Loxo through the connectorClaude → Loxo

    Loxo's official connector (MCP). It only runs while someone is typing; it cannot score on its own, which is why Path A exists.

  3. Claude answers from the firm's real dataLoxo

    Including the scorecards Weaver wrote in Path A, so the answer can use the scores, signals and watch items.

Path C · phase 2, prepared

The client pipeline report

Built and tested on sample data, not switched on or sold yet. Today it runs from your Mac with one command; later it can be a button.

  1. Ask for the report of one searchYour Mac, for now

    npm run report:client -- --loxo-job 45 --results data/runs/…/job-45.json

  2. Weaver reads the search from LoxoLoxo, read only

    Every candidate, their stage (outbound, responded, first screen, cleared, submitted), pay fields, and any scorecard the team wrote themselves.

  3. Weaver lays out the reportWeaver

    Cover with the funnel, top ten ranked, where the search stands, a profile page per finalist, the team's own scorecard, then the screened, responded and outbound lists. Their navy and blue.

  4. Claude writes only the short textClaude

    The cover line, "how to read the pipeline" and "where we're focusing next". It sees C1, C2… instead of names, and never pay. Names go back in afterwards.

  5. The team edits the draft in the browserPeople

    Click any text to change it, reorder the top ten, add the pay picture and what they learned on calls.

  6. Save as PDF and send to the clientPeople

    The client sees only what the team checked. Scores shown to the client come from the team's own scorecards, never from Weaver's first read.

Once per search

Setting a search's scorecard

  1. Draft the nine criteria from the jobClaude

    npm run scorecard:draft -- --provider claude --loxo-job 45

  2. Josh approves or changes themPeople

    You send him the short text file it makes. One minute for him.

  3. Approve, commit, and Render picks it upGitHub → Render

    npm run scorecard:draft -- --approve 45

    Then commit and push. Render deploys the new file. This is why Render's automatic deploy has to work before go-live.
